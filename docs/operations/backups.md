# YGo backups and recovery (#130)

Owner-operated procedure for ADR-0005. [Monitoring](monitoring.md) owns the >30-day off-AWS-copy alarm; [timed jobs](timed-jobs.md) schedule the nightly dump and weekly RDS snapshot. #35 owns real AWS provisioning and the timed pre-launch drill. Never put a database URL, dump, password or recovery key in Git. All AWS resources below are in `ap-south-1`.

## Provision and check retention

1. In RDS, set production instance automated backup retention to **7 days** and deletion protection on. Verify `aws rds describe-db-instances --region ap-south-1 --db-instance-identifier INSTANCE --query 'DBInstances[0].[BackupRetentionPeriod,DeletionProtection]'` returns `7, True`. Check this after any instance replacement; RDS defaults may differ. Automated restore/PITR creates a **new** instance, never the original.
2. Create a dedicated private S3 backup bucket (not the versioned photo bucket), Block Public Access on all four settings, default SSE-S3 or SSE-KMS encryption, **never enable versioning**, and no public policy/ACL. Add exactly one enabled lifecycle rule: prefix `nightly/`, current-object expiration **30 days**, no earlier transition/expiration rule. In console review the JSON; the nightly command rejects drift. Confirm `aws s3api get-bucket-versioning --bucket BUCKET --region ap-south-1 --query Status --output text` says `None`. Review `get-public-access-block`, `get-bucket-encryption` and `get-bucket-lifecycle-configuration`; record the results without secrets. Lifecycle may expire later than day 30, not earlier; monitor actual objects and investigate drift. Do not use this bucket for photos or deployments.
3. Grant the host role only `s3:PutObject`/`GetObject` on `BUCKET/nightly/*` and read access to the bucket's lifecycle/versioning checks. No `s3:ListBucket` is needed. Grant `rds:CreateDBSnapshot` on the production DB instance **and** `ygo-weekly-*` snapshot resources, `rds:DescribeDBSnapshots` on that instance and those snapshots, and `rds:DeleteDBSnapshot` only on `ygo-weekly-*` snapshots in `ap-south-1`. [RDS lists these resource types](https://docs.aws.amazon.com/service-authorization/latest/reference/list_rds.html). Keep S3 and RDS access on the instance role, not static keys. Install reviewed `ops/backup.sh` as root-owned mode 0700 `/opt/ygo/ops/backup.sh`.

Before enabling the nightly timer, run `sudo install -d -o root -g root -m 0700 /var/tmp/ygo-backup` and confirm `stat -c '%u:%g:%a' /var/tmp/ygo-backup` is `0:0:700`. Check `findmnt -n -T /var/tmp/ygo-backup -o FSTYPE` reports a disk-backed filesystem, not `tmpfs` or `ramfs`; the script rejects memory-backed storage. The backup service's `StateDirectory=ygo` creates root-only `/var/lib/ygo`; check it is `0:0:700`. The script stores only the byte count of the last fully verified dump in its mode-0600 `/var/lib/ygo/backup-last-bytes`. It clears stale files in the fixed workspace at startup and deletes the dump, downloaded verification copy, and digests on exit, including failure. A killed job may leave plaintext until the next run; restrict host access and investigate a failed timer promptly. File deletion does not securely erase SSD blocks, so keep the host volume encrypted.

The free-space gate runs before dumping: it requires **2 × the last verified dump size + 512 MiB**, or **2 GiB** when the size record is missing. A malformed record fails the job. If available bytes are below the requirement, the job reports the required and available byte counts and does not start `pg_dump`. A larger than usual new dump can still fill the disk; monitor actual size and adjust host capacity before the next run.

The `backup-nightly` [job](timed-jobs.md) invokes `/opt/ygo/ops/backup.sh dump BUCKET` nightly as root; it makes a custom-format dump from `/etc/ygo/production.env`, fully reads it with `pg_restore`, uploads archive and SHA-256, downloads both and verifies again. A nonzero exit is failure even if S3 contains partial objects; the job records success only on exit zero. The `snapshot-weekly` job runs each Monday at 06:00 IST, waits up to 170 minutes for RDS to report `available`, then deletes only `ygo-weekly-YYYYMMDD` snapshots older than 35 days. A still-creating snapshot remains in RDS if the job times out; investigate before retrying. Check the RDS snapshot list after each run; do not manually label unrelated snapshots with this prefix.

**Operator proof on #35, before closing #175:** On the production host, privately compare `df -B1 --output=avail /var/tmp/ygo-backup` with twice the latest verified dump's actual byte size plus 512 MiB (or 2 GiB for the first run). Confirm the path is disk-backed and the override shows `PrivateTmp=false`, `ReadWritePaths=/var/tmp`, and `StateDirectory=ygo`. Run one `sudo systemctl start ygo-job@backup-nightly.service`. Confirm its `job_runs` row is `ok`, the S3 archive and digest were verified, `/var/lib/ygo/backup-last-bytes` equals that archive's byte count, and `/var/tmp/ygo-backup` is empty afterward. Record measurements and result in the private operator log; do not paste identifiers or dump data into the issue or PR. Leave #175 open after merge until this proof passes.

## Monthly off-AWS copy (operator, every 30 days)

Use a personally controlled removable drive; no second cloud account or sync folder. Install the AWS CLI, GnuPG and PostgreSQL 17 client on the workstation. In the owner's calendar, create an alert **30 days after the last verified copy** (or today if none exists), titled `YGo off-AWS copy overdue`; do not dismiss it until a new copy is verified, then move the alert to 30 days after that copy. #131 adds an independent >30-day monitoring alarm. Keep an offline paper log with UTC copy date, S3 object/date, SHA-256, drive identifier, verification result, and old-copy wipe date. Keep it separately from the drive. Two copies maximum and no copy at or past 90 days.

1. Before first use, encrypt the **whole drive**: macOS Disk Utility → View → Show All Devices → select the verified removable physical device → Erase → GUID Partition Map + APFS (Encrypted); Windows Control Panel → BitLocker Drive Encryption → BitLocker To Go → turn on for the verified removable drive → encrypt **entire drive**; Linux identify device by serial with `lsblk -o NAME,SIZE,MODEL,SERIAL`, double-check it is not a system disk, then `sudo cryptsetup luksFormat --type luks2 /dev/disk/by-id/EXACT-DEVICE` and `sudo cryptsetup open ... ygo-offline`, format the mapped device, mount it. These erase a device; do them only after confirming its identifier and that no wanted data remains. Store the drive-unlock/recovery key on paper in a different locked place, never on the drive, AWS, or a synced password manager.
2. Unlock/mount and check drive identifier and free space. If two copies already exist or the oldest will reach 90 days before the next scheduled copy, **wipe the oldest first**: remove only its encrypted `YYYYMMDD.dump.gpg` and digest, destroy that copy's unique offline passphrase record, and write wipe UTC date in the log. Do not reuse a passphrase. If any copy is already 90 days old, stop and investigate the retention breach, then remove it immediately. Keep the whole-drive encryption enabled throughout.
3. Choose the latest verified nightly archive in S3. Download its `.sha256` to the encrypted drive. In bash first run `set -o pipefail`, then stream directly into a second layer of encryption: `aws s3 cp s3://BUCKET/nightly/YYYYMMDD.dump - --region ap-south-1 | gpg --symmetric --cipher-algo AES256 --output /MOUNT/YYYYMMDD.dump.gpg`. On Windows use `cmd /d /c "aws s3 cp s3://BUCKET/nightly/YYYYMMDD.dump - --region ap-south-1 | gpg --symmetric --cipher-algo AES256 --output X:\YYYYMMDD.dump.gpg"`; `cmd` preserves binary pipe bytes, unlike older PowerShell versions. Enter a **new unique** passphrase interactively and keep it only in a labeled paper envelope stored separately. If either pipe command fails, remove the incomplete file and do not log success.
4. Verify by `gpg --decrypt /MOUNT/YYYYMMDD.dump.gpg | sha256sum` against the downloaded S3 digest, then `gpg --decrypt /MOUNT/YYYYMMDD.dump.gpg | pg_restore --file=/dev/null`; bash `pipefail` makes either process failure visible. On Windows, use `cmd /d /c "gpg --decrypt X:\YYYYMMDD.dump.gpg | openssl dgst -sha256"` and compare the hash, then `cmd /d /c "gpg --decrypt X:\YYYYMMDD.dump.gpg | pg_restore --file=NUL"`; check both programs' success, not just the final command's exit code. Never copy plaintext to the system disk. Eject/lock the drive, then record verification and copy dates. An unverified copy does not reset the overdue clock.

Deleting a file alone is not secure sanitization, especially on SSDs. The unique per-copy GnuPG passphrase is the cryptographic disposal boundary: destroy the only record of that passphrase after deleting its file, then verify it cannot be recovered from another key store. For whole-drive retirement, an HDD may be overwritten end-to-end with a verified device erase; an SSD needs the vendor's sanitize/secure-erase or verified cryptographic erase, not a file overwrite. If the device cannot report a successful sanitize operation, use certified physical destruction. Record device serial, method, verification and date. See [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final).

## Production restore (do not begin until #92 replay exists)

1. Pick a verified archive and its `.sha256`, or restore RDS automated backup/weekly snapshot to a **new** RDS instance. For an RDS restore, dump the recovered production database to a custom archive and calculate its SHA-256. Never target the existing production database. Create a separate, **fresh empty** PostgreSQL/PostGIS-capable database and owner role for recovery, with network/TLS restrictions matching production. Do not preinstall PostGIS in the empty database; the archive restores it. Confirm its hostname and database name differ from current production.
2. Place a root-owned mode-0600 `/etc/ygo/recovery.env` with the same environment-file fields as production but `DATABASE_URL` pointing only to the fresh target. Keep `/etc/ygo/production.env` unchanged. Download archive/digest to a root-only directory on the host through SSM, then run `sudo bash /opt/ygo/ops/restore.sh ARCHIVE SHA256_FILE /etc/ygo/recovery.env`. Time from before invocation until successful service start and record elapsed time, source, target and verification in the private operator log. Do not paste URLs or logs with secrets into issues.
3. The script disables/stops `ygo@production` first, rejects same/occupied targets, verifies archive SHA-256 and full readability, restores with transaction/error-stop, checks public tables, invokes `/opt/ygo/production/current/replay-deletions.js` under the recovery URL, then atomically switches config, starts the unit and checks local `/v1/healthz`. Missing or failing replay (until #92 ships), or failed health, leaves service off and original config intact. On **any** failure keep it off; investigate and repeat with a **new empty target**, never reuse a partly restored one. Do not manually bypass replay or start the unit. After success check public `/v1/healthz`, representative restored rows, deletion erasures, and log the measured recovery time.

CI exercises the exact restore script against local PostGIS on every PR, including corrupt archive, failed restore, missing/failing replay, preserved production config and stopped service. The one real AWS drill before launch belongs to #35, after #92 exists; record its elapsed time there.
