# YGo timed jobs (#131 part 2b)

Part 2a supplies `job_runs` and the one-shot command. The template schedules `backup-nightly`, `cleanup-sessions`, `expire-orders` (#57) and `snapshot-weekly`, each with its own freshness metric and alarm. All units run on the production AL2023 host in `ap-south-1`; no agent creates AWS resources.

## Install and start

Complete [backup setup](backups.md), deploy a release containing `job.js` and `check-jobs.js`, and migrate its database before enabling timers. Verify the existing `/opt/ygo/ops/backup.sh` is root-owned and mode 0700. The instance role needs the backup S3 permissions, the [production-scoped RDS snapshot permissions](backups.md), and `cloudwatch:PutMetricData` for namespace `YGo` from [monitoring](monitoring.md). No access keys belong on the host.

Create root-owned mode-0600 `/etc/ygo/backup.env` containing `BACKUP_BUCKET=<dedicated-backup-bucket>` and `RDS_INSTANCE_ID=<production-rds-instance>` using identifiers from the private operator log. Do not commit or paste their values into a PR. The production database URL remains only in `/etc/ygo/production.env`. The backup and snapshot services read both files; cleanup and the checker read only the production file. Install these reviewed files as root-owned under `/etc/systemd/system/`:

- `ops/ygo-job@.service` and `ops/ygo-job@.timer`
- `ops/ygo-job@backup-nightly.service.d/override.conf`
- `ops/ygo-job@backup-nightly.timer.d/override.conf`
- `ops/ygo-job@cleanup-sessions.timer.d/override.conf`
- `ops/ygo-job@expire-confirmations.timer.d/override.conf`
- `ops/ygo-job@expire-orders.timer.d/override.conf`
- `ops/ygo-job@snapshot-weekly.service.d/override.conf`
- `ops/ygo-job@snapshot-weekly.timer.d/override.conf`
- `ops/ygo-job-check.service` and `ops/ygo-job-check.timer`
- `ops/ygo-job-check-expire-orders.service` and `.timer` (every 5 minutes)
- `ops/ygo-job-check-expire-confirmations.service` and `.timer` (every 5 minutes)

Keep the override directories with the same names. The template runs as `ygo-production` with the API unit's filesystem and privilege hardening. Backup and snapshot alone override to root because `backup.sh` requires root. The backup override sets `PrivateTmp=false` so the parent and transient `pg_dump` unit see the same `/var/tmp/ygo-backup` path; `ReadWritePaths=/var/tmp` permits writes under `ProtectSystem=strict`, and `StateDirectory=ygo` permits the root-only size record in `/var/lib/ygo`. The backup script verifies S3 lifecycle, dump readability, upload digest, download digest and downloaded archive before recording `ok`. The snapshot script records `ok` only after RDS reports `available` and retention succeeds. It polls for up to 170 minutes, leaving ten minutes of the service's three-hour timeout for retention. Failures store fixed `backup failed` or `snapshot failed` text; details stay in journald.

`cleanup-sessions` also deletes old `job_runs` rows (#520), because `expire-orders` writes about 1,440 a day. After the session cleanup commits, a second transaction deletes `ok` rows older than 30 days, `failed` rows older than 180 days and `running` rows (a crashed run) older than 30 days. Per job it always keeps the latest finished row and the latest `ok` row, whatever their age, because the checker reads exactly those two. A failure in this second step fails the `cleanup-sessions` run (`cleanup failed`) but cannot undo the session cleanup. The periods are `JOB_RUN_OK_KEEP_DAYS` and `JOB_RUN_FAILED_KEEP_DAYS` in `apps/server/src/jobs.ts`. Two indexes back the checker's two queries and the cleanup: `(job_name, finished_at DESC NULLS FIRST)` and the same columns `WHERE status = 'ok'`. Measured on a year of data (525,000 `expire-orders` rows): both checker queries are index scans (3 ms and under 1 ms), the first cleanup removes the backlog in about 0.55 s, and a daily cleanup takes about 22 ms.

Every job reads only `DATABASE_URL` and the order timing from `/etc/ygo/production.env`. `cleanup-sessions` also reads `VISIT_PHOTO_BUCKET`, `PRODUCT_IMAGE_BUCKET` (it must differ from `VISIT_PHOTO_BUCKET`), `S3_REGION` and `S3_ENDPOINT` (when the bucket is set) to delete expired delivery photos (#56, #524); the other jobs read none of them, and an invalid value fails `cleanup-sessions` alone.

`expire-orders` (#57, ORD-2) moves each `placed` order older than `ORDER_EXPIRE_SECONDS` to Expired, one transaction per order (status, history row and the customer's notification together), and records `expiry failed` in `job_runs` when any order could not be moved. It reads `ORDER_REALERT_SECONDS` and `ORDER_EXPIRE_SECONDS` from `/etc/ygo/production.env`, the same file as the API, so both always agree. The apps count down from 600 seconds, so changing `ORDER_EXPIRE_SECONDS` also needs an app update that changes `ORDER_ANSWER_SECONDS` in `@ygo/contracts`, until the order responses carry the server's deadline. Locally, run it by hand: `node apps/server/dist/job.js expire-orders`.

`expire-confirmations` (#64) moves each order in `awaiting_customer_confirm` whose proposal deadline `confirm_by_at` has passed to `cancelled_by_customer` (actor system, reason `no_confirmation`), marking the proposal expired and recording `confirmation expiry failed` in `job_runs` if an order could not be moved. Locally, run it by hand: `node apps/server/dist/job.js expire-confirmations`.

Run `sudo systemd-analyze verify ygo-job@backup-nightly.service ygo-job@backup-nightly.timer ygo-job@cleanup-sessions.service ygo-job@cleanup-sessions.timer ygo-job@expire-confirmations.service ygo-job@expire-confirmations.timer ygo-job@expire-orders.service ygo-job@expire-orders.timer ygo-job@snapshot-weekly.service ygo-job@snapshot-weekly.timer ygo-job-check.service ygo-job-check.timer ygo-job-check-expire-orders.service ygo-job-check-expire-orders.timer ygo-job-check-expire-confirmations.service ygo-job-check-expire-confirmations.timer`, then `sudo systemctl daemon-reload`. Inspect `systemctl cat` for all five job instances and the checker. Start each job once with `sudo systemctl start ygo-job@JOB.service` (including `ygo-job@expire-confirmations.service`). Check exit status, journal, the verified S3 archive/digest, the RDS snapshot's `available` status, and `job_runs` rows. A second snapshot start on the same UTC date uses the same snapshot name and fails; inspect the existing snapshot before retrying. Then start `sudo systemctl start ygo-job-check.service` and inspect all five `YGo/JobHealthy` series, each with its `JobName` dimension. A job with no successful run is unhealthy.

Only after these checks, run `sudo systemctl enable --now ygo-job@backup-nightly.timer ygo-job@cleanup-sessions.timer ygo-job@expire-confirmations.timer ygo-job@expire-orders.timer ygo-job@snapshot-weekly.timer ygo-job-check.timer ygo-job-check-expire-orders.timer ygo-job-check-expire-confirmations.timer` and inspect `systemctl list-timers`. The overrides set 20:30 UTC nightly backup, 22:30 UTC cleanup, **Monday 00:30 UTC (06:00 IST)** snapshot, and runs of `expire-orders` and `expire-confirmations` every minute; the daily checker runs at 01:30 UTC for the jobs, and `ygo-job-check-expire-orders.timer` and `ygo-job-check-expire-confirmations.timer` run the same checker for `expire-orders` alone (`check-jobs.js expire-orders`) and `expire-confirmations` alone (`check-jobs.js expire-confirmations`) every 5 minutes. All use `Persistent=true`. A missed firing runs after the host returns. The checker has its own unprivileged unit; it is not a job and writes no `job_runs` row. It ignores running rows: a latest **finished** failure reports 0; otherwise a success older than its limit (26 hours for daily jobs, 15 minutes for `expire-confirmations` and `expire-orders`, eight days for snapshots) or no success reports 0. Database read failures report 0 for every job; a missing or invalid database URL publishes nothing, so missing data breaches. A failed metric publish exits nonzero, leaving the missing-data alarm to report trouble. The checker uses the instance role, not AWS keys.

After the first checker metrics arrive, rerun the reviewed `ops/monitoring.sh` as the operator and confirm all job alarms use the existing Mumbai SNS topic with confirmed email subscription. Each evaluates the Minimum `JobHealthy` value, threshold <1, missing data breaching: over one day for the daily-checked jobs, and over two 5-minute periods for minutely jobs: a failed run alarms in about 10–15 minutes, an overdue run about 25–30 minutes after its last success (15-minute limit, then the next check, then two periods). A future job must add its timer, age limit, metric dimension and alarm in the same feature ticket.

## Prove alarm and recovery

`pnpm gate`, real-Postgres job/freshness tests, the slow-snapshot/retention script test, and AL2023 `test-systemd-compat.py` must pass in CI. On the host, record successful runs of all five jobs, the verified S3 object, the `available` RDS snapshot, and `job_runs` rows. Confirm the checker emits 1 for all five dimensions (run `ygo-job-check-expire-orders.service` for `expire-orders` and `ygo-job-check-expire-confirmations.service` for `expire-confirmations`). For each alarm, use a controlled maintenance window and publish **0 to its actual `YGo/JobHealthy` metric series** with `aws cloudwatch put-metric-data --region ap-south-1 --namespace YGo --metric-name JobHealthy --dimensions JobName=JOB_NAME --value 0 --unit Count`. Confirm ALARM and email; then run the real job and checker and confirm a 1 is published. For the three daily alarms, which use the one-day Minimum, the 0 can keep it in ALARM until the next daily evaluation window. Confirm return to OK and the recovery email then. Record metric history and emails privately; never paste account IDs, ARNs, database URLs or bucket names into the PR. If any metric, timer, alert or recovery fails, activation is incomplete.

The separate >30-day off-AWS removable-drive alarm and calendar reminder stay as described in [backups](backups.md). A successful S3 dump never proves an off-AWS copy.
