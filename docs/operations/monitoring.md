# YGo monitoring (#131)

Operator-run in AWS only. The EC2 instance and RDS database stay in `ap-south-1`. Route 53 is global; its health metric, CloudWatch alarm and SNS email topic must be in `us-east-1` ([AWS](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/monitoring-health-checks.html)). No agent runs these provisioning commands. [Timed jobs](timed-jobs.md) add the nightly backup, cleanup and job staleness checks.

## Before activation

Complete [provisioning](provisioning.md): account budgets, public production DNS and valid HTTPS certificate, production `/v1/healthz` returning `200` only when RDS answers, `ygo@production` running, private RDS, and an instance role. Complete [backup setup](backups.md), including its separate calendar reminder. Confirm `LOG_LEVEL=info` in the production SSM environment document. Keep identifiers and recipients in the private operator log; never paste their values or logs containing secrets into Git or a PR.

In SSM Parameter Store in Mumbai, set `/ygo/ops/alarm-email` as SecureString to the alert recipient and `/ygo/ops/off-aws-verified-at` as String to the UTC completion instant of the **last verified** removable-drive copy, in `YYYY-MM-DDTHH:MM:SSZ` form. If none exists, leave the verification date absent: the check must report unhealthy. Update it only after all verification steps in [backups](backups.md) succeed; preserve the offline paper log. An unverified copy never resets the clock. The owner runs `ops/monitoring.sh` from a reviewed checkout with an AWS CLI profile authorized to create Route 53 health checks, two SNS topics/subscriptions, three CloudWatch log groups and filters, and CloudWatch alarms. Do not give that provisioning policy to the EC2 role.

Add to the **instance role**, scoped where AWS supports it: `ssm:GetParameter` for `/ygo/ops/off-aws-verified-at`; `cloudwatch:PutMetricData` conditioned to namespaces `YGo` and `CWAgent`; `logs:DescribeLogGroups` (resource `*`); and `logs:CreateLogStream`, `DescribeLogStreams`, `PutLogEvents` and `PutRetentionPolicy` for `/ygo/api/*` and `/ygo/systemd`. The operator script creates log groups; the agent does not need `CreateLogGroup`. The AWS managed `CloudWatchAgentServerPolicy` works but is broader. Use the instance role, never access keys. The operator's monitoring script needs `ssm:GetParameter` for the email parameter; the host does not.

On AL2023, install the agent with `sudo dnf install amazon-cloudwatch-agent`, then check `sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status`. Journald collection needs **1.300070.0 or newer** ([AWS announcement](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-cloudwatch-agent-journald/)); the AL2023 repository may lag. If older, run `curl -fL -o /tmp/amazon-cloudwatch-agent.rpm https://amazoncloudwatch-agent.s3.amazonaws.com/amazon_linux/arm64/latest/amazon-cloudwatch-agent.rpm` ([AWS install guide](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/manual-installation.html)), then `sudo dnf install /tmp/amazon-cloudwatch-agent.rpm`, and check the version again. Copy the reviewed `ops/cloudwatch-agent.json` to a root-owned file on the host, then run `sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -c file:/opt/ygo/ops/cloudwatch-agent.json -s`. The agent ships production and staging journald messages, including pino JSON, to separate log groups with **seven-day** retention. It collects root-disk used percent and available-memory percent once a minute. Inspect `systemctl status amazon-cloudwatch-agent` and recent CloudWatch log events. Activation is incomplete until new production requests are visibly flowing to `/ygo/api/production`. Journald records may contain a pino JSON line inside `body.MESSAGE`. The `/ygo/systemd` group matches manager records whose `UNIT` field names production, because the start-limit message is emitted by systemd rather than the API process.

Install `ops/off-aws-check.py` under `/opt/ygo/ops/`, and its dedicated service/timer in `/etc/systemd/system/`, all root-owned. Run `sudo systemctl daemon-reload`, `sudo systemctl start ygo-off-aws-check.service`, then `sudo systemctl enable --now ygo-off-aws-check.timer`. Inspect the service exit status and the `YGo/OffAwsCopyHealthy` metric. The daily check publishes **1** only for a valid, non-future UTC date no older than exactly 30 days. A missing, malformed, impossible, future or older date, or failed SSM read publishes **0** and exits nonzero. If publishing fails too, it exits nonzero and the alarm's missing-data setting reports unhealthy. The timer is independent of the later reusable job template and touches no database.

From the reviewed checkout, after the first metric and agent data are visible, run `bash ops/monitoring.sh <production-api-host> <ec2-instance-id> <rds-instance-id>`. It is safe to rerun for these same resources; review existing health checks before changing the host name. Confirm **both** SNS email subscriptions using their confirmation emails. Inspect the two topic subscriptions for `Confirmed` and all ten alarms for the intended topic, metric and region before relying on them. The two job alarms report missing data until [timed jobs](timed-jobs.md) are activated; do not treat monitoring as complete before those checks flow.

## Alarm meaning and response

Route 53 uses exactly three checker regions (`us-east-1`, `eu-west-1`, `ap-southeast-1`). Each checker probes HTTPS every 30 seconds and marks the endpoint unhealthy after three consecutive failed probes **per checker**. That is separate from the `HealthCheckStatus` alarm, which evaluates a one-minute minimum below 1. SNS sends email on the alarm state transition; [AWS says several minutes can elapse](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/monitoring-health-checks.html). Do not interpret 3 × 30 seconds as an email-delivery guarantee. The health route checks RDS, so a failed database also fails the public check. No DNS failover is configured.

The 5xx numerator counts **completed production requests** whose pino `res.statusCode` is 500–599. The denominator counts **all completed production requests**, including Route 53 health probes. A phrase filter counts completions; a regex filter finds 5xx codes in raw pino lines or journald-wrapped lines. The five-minute expression is `IF(all>=20,100*errors/all,0)`. It alarms at **≥5%** only with at least **20** completed requests in the window. Health probes add to that total, so at low real-user traffic, errors can appear in logs before the rate alarm fires. With 1–19 requests, it evaluates to 0; no traffic normally means lost health probes too and must be investigated. If log telemetry is absent, the expression has no data and sends an `INSUFFICIENT_DATA` email instead of claiming a 0% error rate. The external health alarm remains independent of log shipping.

| Alarm | Trigger | What it means / what to do |
| --- | --- | --- |
| `ygo-health` | Route 53 status <1, 1 × 1 minute (`us-east-1`) | Public HTTPS or RDS is unavailable. Check DNS/TLS, Nginx, `ygo@production`, then RDS and its logs. |
| `ygo-5xx-rate` | ≥5% with ≥20 completions, 1 × 5 minutes | Server errors rose. Inspect production pino errors and the last deploy. `INSUFFICIENT_DATA` means inspect the agent/log stream. |
| `ygo-ec2-cpu` | ≥80% average, 3 × 5 minutes | Host saturated. Inspect processes and CPU credits; staging shares this host. |
| `ygo-rds-cpu` | ≥80% average, 3 × 5 minutes | RDS CPU saturated. Inspect RDS connections and slow queries; check staging workload. |
| `ygo-root-disk` | Root used >85% average, 2 × 5 minutes | Less than 15% free. Inspect journal usage, releases and temporary files before removing reviewed data. |
| `ygo-memory` | Available <15% average, 2 × 5 minutes | Host memory pressure. Inspect processes and OOM messages; check both API units. |
| `ygo-crash-loop` | systemd start limit hit ≥1, 1 × 5 minutes | Production restarted five times rapidly and stopped. Inspect `journalctl -u ygo@production`, fix the cause, then reset/start the unit. |
| `ygo-off-aws-copy` | Healthy metric <1, 1 × 1 day; missing breaches | The verified removable-drive copy is overdue or the check failed. Inspect SSM date, timer and paper log; complete and verify a new copy before updating SSM. |
| `ygo-job-backup-nightly` | `JobHealthy{JobName=backup-nightly}` <1, 1 × 1 day; missing breaches | Latest finished backup failed, last success is >26 hours old, or the checker cannot report. Inspect its timer, `job_runs`, backup journal and verified S3 object. |
| `ygo-job-cleanup-sessions` | `JobHealthy{JobName=cleanup-sessions}` <1, 1 × 1 day; missing breaches | Latest finished cleanup failed, last success is >26 hours old, or the checker cannot report. Inspect its timer, `job_runs` and journal. |

CPU and agent metrics use instance identifiers at activation, never committed IDs. Missing EC2/RDS/agent metrics breach; investigate missing telemetry as well as host health. Crash-loop metric absence is normal. The off-AWS date never comes from `job_runs` or an S3 object: neither proves a verified copy left AWS.

## Prove activation and recovery

1. `pnpm gate` must pass in the PR. On AWS, confirm each alarm's metric receives data, its dimensions and threshold match this table, the CloudWatch log groups retain seven days, and the agent/timers are active. Confirm the two SNS subscriptions before testing delivery.
2. For the **original eight alarms**, while their real state is healthy, run `aws cloudwatch set-alarm-state --region REGION --alarm-name ALARM --state-value ALARM --state-reason 'operator delivery test'`. Use `us-east-1` only for `ygo-health`, Mumbai for the other seven. Record each ALARM transition in CloudWatch alarm history and the received email. Wait for real metric evaluation to restore OK, then record the OK transition and recovery email. For the two job alarms, follow the [real-metric proof](timed-jobs.md#prove-alarm-and-recovery). If a real alarm is already active, resolve it first; never force a healthy state over an incident. [AWS documents](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/API_SetAlarmState.html) that this test state is temporary and can be replaced within seconds, so use history rather than only the current console state.
3. Also exercise the **source path**: request `/v1/healthz` publicly and check Route 53 health; send a normal production request and find its pino line in `/ygo/api/production`. Copy one real CloudWatch log event message locally (including its wrapper, if present) and run `aws logs test-metric-filter --region ap-south-1 --filter-pattern '"request completed"' --log-event-messages "$event"`, then repeat with `--filter-pattern '%statusCode\\?\x22[ ]*:[ ]*5[0-9][0-9]%'`. Test the same two patterns against reviewed 200 and 503 completion samples in that observed format: the completion pattern must match both, and the 5xx pattern must match the 503 but not the 200. Activation is incomplete until these results and flowing agent logs are confirmed. Confirm systemd's start-limit phrase matches its metric filter without deliberately crash-looping production; run the off-AWS service with an invalid date in a controlled maintenance window and restore the original SSM date immediately. For the off-AWS check, verify it emits 0 and exits nonzero, then emits 1 after restoration. Confirm an absent-date/SSM-read failure also emits 0 in the local tests. Record results in the private operator log, excluding values and account identifiers from the PR.
4. Review `ygo-5xx-rate` during a quiet five-minute window: fewer than 20 completions is OK, while missing log telemetry becomes `INSUFFICIENT_DATA` with email. If any alert, recovery email, metric, or source test fails, activation is incomplete. Keep manual checks from provisioning and backups until fixed.

## Cost

**Part 1 estimate, subject to current regional pricing:** about **USD 4–5/month** for its eight standard alarms (metric math may count multiple alarm metrics), roughly six custom metrics, two SNS email topics, one AWS-endpoint HTTPS health check, and about 1 GB/month of logs at seven-day retention. Part 2b adds two standard alarms and two per-job custom metric series; check their current Mumbai prices before activation. Tax, log volume and any changed AWS price are additional. Check [CloudWatch](https://aws.amazon.com/cloudwatch/pricing/) and [Route 53](https://aws.amazon.com/route53/pricing/) pricing for the live account before activation; the HTTPS feature can incur a charge even when the basic AWS-endpoint health check is free.
